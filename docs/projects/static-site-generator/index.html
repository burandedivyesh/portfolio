Static Site Generator

This website isn't built using a traditional website framework or an existing static site generator. It's powered by a small Markdown-to-HTML generator that I built myself.

What started as a programming exercise has become something I use to maintain my own corner of the internet.

How It Started

This project began as a programming exercise where I set out to understand how Markdown documents could be transformed into static HTML pages.

What initially started as a learning exercise gradually became something more practical when I decided to use the generator to power my own portfolio website.

Using it for a real website introduced new challenges around content organisation, templates, styling, and deployment.

How It Works

At a high level, the generator takes Markdown content, converts it into HTML, and places that content inside a shared HTML template.

The process can be broken down into a few steps:

  1. Read the Markdown source files.
  2. Identify block-level Markdown elements.
  3. Parse supported inline elements within those blocks.
  4. Convert the parsed elements into HTML.
  5. Insert the generated HTML into a shared template.
  6. Copy static assets such as CSS files and images.
  7. Write the generated website files to the output directory.

The resulting website consists of static HTML, CSS, and images that can be hosted using GitHub Pages.

Markdown Support

The generator currently supports a deliberately limited subset of Markdown.

Block-level elements include:

  • Headings
  • Paragraphs
  • Blockquotes
  • Ordered lists
  • Unordered lists
  • Code blocks

Inline elements include:

  • Plain text
  • Bold text
  • Italic text
  • Links
  • Images
  • Inline code

Blocks are separated using blank lines.

The parser doesn't currently support nested inline formatting, so combinations such as bold text containing a link are outside its supported syntax.

Using It for This Website

After completing the initial project, I decided to use the generator to build my own portfolio.

This introduced a practical challenge: instead of generating a sample website once, I needed something I could maintain and update regularly.

I started organising content into separate Markdown pages, using a shared HTML template and CSS stylesheet to provide a consistent appearance.

The website now includes project pages, an About page, and a learning journal.

Using the generator for a real website has helped me identify which features work well and which limitations might be worth addressing next.

Design Decisions

One decision I've maintained is keeping content separate from presentation.

Markdown files describe the content of each page, while the HTML template provides the shared document structure and CSS handles visual styling.

Another important decision is keeping the generator simple enough that I can understand and maintain it.

Rather than immediately supporting every Markdown feature, I've focused on using the existing capabilities reliably.

Current Limitations

There are several areas where the generator could be improved.

  • Nested inline Markdown elements are not supported.
  • Complex Markdown structures are outside the current parser's capabilities.
  • The available Markdown syntax limits more advanced page layouts.
  • Additional validation and automated testing could help prevent regressions as the parser evolves.

These limitations haven't prevented me from building the portfolio, but they provide a useful direction for future development.

What I've Learned

One of the most interesting parts of this project has been seeing how a relatively small tool can become useful beyond the exercise it was originally built for.

Building the parser helped me understand the structure of Markdown and HTML. Using the generator to maintain this portfolio has made me think more carefully about templates, file organisation, styling, and deployment.

It's also reminded me that a project doesn't need to support every possible feature to be useful.

What's Next

I plan to continue improving the generator as I use it.

Some possibilities include:

  • Supporting nested inline elements
  • Improving parser reliability
  • Expanding automated tests
  • Improving template flexibility
  • Simplifying the build and deployment workflow

Rather than implementing everything at once, I'd like future improvements to be guided by problems I encounter while maintaining this website.
